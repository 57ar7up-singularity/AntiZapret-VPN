## Рабочий сервер: Germany X

| Параметр | Значение | Откуда известно |
|---|---|---|
| `ROUTE_ALL` | `y`, установлен 2026-09-10 | со слов владельца |
| Остальные `*_INCLUDE` | значения по умолчанию из `setup.sh` | не проверялось |

**`ROUTE_ALL=y` — штатный и оптимальный режим этой установки. Исходить из него
по умолчанию.** Не предлагать «добавь домен в `config/include-hosts.txt`» первым
шагом: в этом режиме список включения уже покрывает всё, и такой совет
бессмысленен. Ручное ведение списков — это режим `ROUTE_ALL=n`, он здесь не
используется.

### Что делает `ROUTE_ALL=y`

`parse.sh:315` дописывает `.` первой строкой `result/include-hosts.txt`, а
генератор на `parse.sh:331` разворачивает её в `*. CNAME .`. Логика
инвертируется:

* через туннель идут **все** домены;
* напрямую — только перечисленное в `result/exclude-hosts.txt`: российские TLD
  (`ru`, `su`, `moscow`, `xn--p1ai`, …) из `download/exclude-hosts.txt`, а также
  VK, Яндекс, Сбер, Авито, Озон, 2GIS, iXBT и всё из `config/exclude-hosts.txt`.

Переключается на живом сервере без переустановки — `update.sh:124` делает
`source setup` до проверки на `update.sh:134`:

```bash
sed -i 's/^ROUTE_ALL=.*/ROUTE_ALL=y/' /root/antizapret/setup
/root/antizapret/doall.sh
```

Конфиги клиентов при этом не меняются: туннель по-прежнему несёт только диапазон
подменных IP, просто в него попадает больше доменов.

### Как из-за этого меняется диагностика

При `ROUTE_ALL=n` первый подозреваемый для «сайт не открывается» — домена нет в
реестре. При `ROUTE_ALL=y` этот вариант почти исключён, и порядок проверки
другой:

1. `/root/antizapret/check-host.sh <url>` — что реально отдаёт DNS АнтиЗапрета.
2. Домен попал в исключения? Российский TLD или CDN из `exclude-hosts.txt`
   (`yastatic.net`, `mycdn.me`, `ngenix.net`) идёт напрямую — это ожидаемое
   поведение, а не поломка. Правится записью в `config/include-hosts.txt`:
   при равной специфичности выигрывает исключение (оно пишется в `proxy.rpz`
   последним), поэтому нужна более точная запись, чем та, что его туда внесла.
3. DNS молчит → `systemctl status kresd@1`, затем `/root/antizapret/doall.sh`.
4. Приложение с зашитым IP, DNS не участвует → `config/include-ips.txt`.
5. Страница грузится частично или рвётся на больших ответах → MTU. Сейчас 1420,
   `mssfix 0`, клампинг MSS через `TCPMSS --clamp-mss-to-pmtu`.

## Модель маршрутизации (не переизобретать)

Решение принимается **на этапе DNS, по домену**, а не по сайту:

* `kresd@1` (127.1.1.1) — DNS АнтиЗапрета. Совпадение с `proxy.rpz` → запрос
  уходит на `proxy.py` (127.3.3.3), тот выдаёт подменный IP из `10.30.0.0/15`
  (альтернативы `172.30.0.0/15` и `198.18.0.0/15`) и ставит DNAT-правило
  подменный→реальный в цепочке `ANTIZAPRET-MAPPING`. Живёт `ttl*2` = 3600 с.
* Нет совпадения → форвард на российские апстримы, клиент получает реальный IP
  и идёт мимо туннеля.
* `kresd@2` (127.2.2.2) — DNS для профилей полного VPN (`vpn-*.ovpn`, `vpn-*.conf`).
* В туннель попадают ровно две вещи: диапазон подменных IP и реальные подсети из
  `result/route-ips.txt` (OpenVPN — `push "route ..."` в `ccd/DEFAULT`,
  WireGuard — `AllowedIPs` из `/etc/wireguard/ips`).
* AAAA отдаётся как `::`, HTTPS/SVCB — NODATA.

Отсюда следует главное: страница тянет ресурсы с десятков хостов, каждый
маршрутизируется независимо. Поэтому при `ROUTE_ALL=n` сайт может открываться
наполовину — часть доменов в списке, часть нет.

## Списки строятся только из доменных источников

`update.sh` тянет `bol-van/rulist/reestr_hostname.txt`,
`antifilter.download/list/domains.lst` и `download/include-hosts.txt`. Ленты
«заблокированные IP» нет ни одной: все `download/*ips.txt` — это диапазоны
хостеров (Cloudflare, Telegram, WhatsApp, Amazon, OVH, …), а не список
блокировок.

Значит блокировка по IP или SNI, когда домена нет в реестре, автоматически не
подхватывается — это ограничение модели, а не баг. Пример: `cybenetics.com`
(`51.91.95.108`, OVH) отсутствует во всех 1 633 311 записях реестра, но его
диапазон `51.80.0.0/12` заблокирован. `ROUTE_ALL=y` закрывает и такие случаи —
ровно поэтому он здесь и выбран.

Промпты `ROBLOX/AMAZON/HETZNER/DIGITALOCEAN/OVH/GOOGLE/AKAMAI_INCLUDE`
закомментированы в `setup.sh:284-311`, но переменные всё ещё пишутся в
`/root/antizapret/setup` (`setup.sh:505-516`) и читаются `update.sh`. Включаются
только правкой файла вручную. Активны при установке лишь
`CLOUDFLARE_INCLUDE`, `TELEGRAM_INCLUDE`, `WHATSAPP_INCLUDE` (`setup.sh:272-282`).

## Доставка изменений на сервер

`update.sh` скачивает `parse.sh`, `update.sh` и `doall.sh` из **апстрима
GubernievS**, а не из этого форка. Правки в этих файлах и новые скрипты
(`check-host.sh`) сами на сервер не приедут — их копируют вручную или
переустанавливают через `setup.sh` из форка. `setup.sh:537` делает `chmod +x`
на всё в `setup/root/antizapret/`, `setup.sh:544` копирует `setup/*` в `/`.
